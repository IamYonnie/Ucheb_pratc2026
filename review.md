## 3. Замечания
### Замечание 1.
- **Файл и место:** `ru/mirea/kt3/domain/Model3D.java`, строка 26.
- **Проблема.** Метод `public Set<Tag> getTags() { return tags; }` возвращает прямую ссылку на внутреннее поле `tags`. Любой вызывающий код может изменить этот `Set` минуя метод `addTag(...)`, например, `model.getTags().clear()` или `model.getTags().add(...)`. Это нарушает инкапсуляцию и позволяет перевести объект в некорректное состояние в обход конструктора и методов.
- **Предложение.** Вернуть неизменяемую проекцию: `return Collections.unmodifiableSet(tags);` или `return Set.copyOf(tags);`.

### Замечание 2.
- **Файл и место:** `ru/mirea/kt3/validation/CompletenessRule.java`, строки 9–14 и 19–21.
- **Проблема.** В классе объявлена константа `private static final List<String> REQUIRED_FIELDS = List.of("id_товароведа", "id_модели", "дата")` и статический геттер `getRequiredFields()` (строки 12–14), но в самом методе `validate()` (строки 19–21) следующие строки продублированы литералами:
  ```
  if (req.getUserId() == null) missing.add("id_товароведа");
  if (req.getModelId() == null) missing.add("id_модели");
  if (req.getDate() == null) missing.add("дата");
  ```
  Таким образом, `REQUIRED_FIELDS` фактически не используется при проверке, а имена полей существуют в двух независимых местах. Если позже список обязательных полей изменят в `REQUIRED_FIELDS`, проверка этому не последует, что приведёт к расхождению.
- **Предложение.** Либо удалить `REQUIRED_FIELDS` и `getRequiredFields()` как неиспользуемые, либо построить проверку на основе `REQUIRED_FIELDS`, чтобы единственным источником истины стал сам список. Это также упростит добавление новых обязательных полей.

### Замечание 3.
- **Файл и место:** `ru/mirea/kt3/catalog/Catalog.java`, строки 42–45.
- **Проблема.** В классе уже есть метод `findProductById(int id)`, возвращающий `Optional<Product>` (строки 35–37), но `modelName(Model3D model)` вместо него обращается напрямую к приватной карте `productsById.get(...)` и вручную проверяет `p != null`. Это дублирует логику поиска продукта и обходит существующий публичный API, нарушая принцип единственной точки доступа к данным.

  ```java

      return findProductById(model.getProductId())
              .map(Product::getName)
              .orElse("(без названия)");
  }
  ```

### Замечание 4.
- **Файл и место:** `ru/mirea/kt3/validation/ValidationResult.java`, строки 10–13.
- **Проблема.** Класс предоставляет статические фабрики `ok()` (строка 15–17) и `fail(List<String>)` (строка 19–21), но при этом оставляет публичный конструктор `ValidationResult(boolean ok, List<String> errors)`. Это позволяет создавать объекты в обход фабрик — например, `new ValidationResult(true, List.of("ошибка"))` (валидный, но с ошибками) или `new ValidationResult(false, List.of())` (невалидный, но без ошибок), то есть в некорректных состояниях. Фабрики как раз и введены, чтобы такие сочетания исключить, но публичный конструктор эту гарантию обнуляет.
- **Предложение.** Сделать конструктор приватным (`private`), оставив создание объектов только через `ok()` и `fail(...)`.

### Замечание 5.
- **Файл и место:** `ru/mirea/kt3/domain/Product.java` (строки 11–16), `ru/mirea/kt3/domain/Model3D.java` (строки 13–19), `ru/mirea/kt3/domain/Tag.java` (строки 9–12), `ru/mirea/kt3/domain/Request.java` (строки 10–15).

Поля `name`, `filePath`, `format`, `status` оказываются `null`, что затем проявляется только при использовании (например, `Catalog.modelName` вернёт `null` вместо имени).

## 4. Исправления в коде по рецензии Дындарь М.В.
### 1. Утечка int[] через standardPositions
- **Проблема:** конструктор копирует только карту эталонных позиций, а значения `int[]` остаются общими ссылками с картой вызывающего.
- **Решение.** Теперь в конструкторе ArScene массивы клонируются

### 2. `availableFiles` - `List` с линейным поиском + пересоздание обёрток в цикле
- **Проблема:** доступные файлы хранятся в `List<String>`, и при каждой проверке ресурса цикл `checkAssets` вызывает `asAssets(availableFiles)` - он строит новый `List<SceneAsset>` размера M, а `ByFileNameRule.check` затем линейно по нему бежит. Для N требуемых и M доступных файлов получается O(N·M) аллокаций и сравнений.
- **Решение.** Вынесла asAssets(...) из цикла и добавила построение Set<String>

### 3. Захардкоженный magic-value `"LAB_01"` в `asAssets`
- **Проблема:** при оборачивании имён доступных файлов в `SceneAsset` идентификатор работы подставляется как строковый литерал `"LAB_01"`. Это бессмысленно для «доступных файлов устройства» (у них нет `labWorkId`) и  жёстко привязывает сцену к demo-данным `Main` (где работа имеет id `LAB_01`).
- **Решение.** Имена доступных файлов в SceneAsset теперь не оборачиваются вообще (выполнялось для пункта 2, поэтому изменения в код не внесены).

### 4. Инвариант «contact == login» у `Student` нарушается через унаследованный `setContact`
- **Проблема:** конструктор `Student` передаёт в `super` пустой contact (`super(id, fullName, "")` на `Student.java:11`), а затем выставляет `setContact(login)`, негласно вводя инвариант «contact равен логину».
- **Решение.** Убрано дублирующее хранение.

### 5. Мёртвый код: три метода без единого вызова
- **Проблема:** `getRequiredFiles` определён, но нигде не вызывается - а в `Main` та же фильтрация продублирована приватным `filterByLab`. `fromLabel` у обоих enum'ов (`Equipment.Type` и `SceneAsset.ResourceType`) тоже не имеет ни одного вызова во всём проекте.
- **Решение.** `fromLabel` добавлен для будущей работы над проектом, поэтому не удалён. Удалила filterByLab, он заменён на расширенный getRequiredFiles, дублирования больше нет.

### 6. `scanner.close()` закрывает `System.in`
- **Проблема:** `Scanner` обёрнут вокруг `System.in`. Закрытие такого `Scanner` закрывает и сам `System.in`
- **Решение.** Убран scanner.close().
